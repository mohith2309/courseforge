## 2025-05-14 - Payment Replay and Weak Audience Validation
**Vulnerability:** The `/payments/verify` endpoint lacked a check to see if an `orderId` had already been processed, allowing a successful payment response to be "replayed" to credit a publisher multiple times for a single purchase. Additionally, the `/auth/exchange` endpoint used `.includes()` for Google ID token audience validation, which could allow bypasses via tokens from other apps if their IDs contained the target project number.
**Learning:** Even with signature verification (like Razorpay's), the application layer must track and idempotently handle transaction IDs to prevent double-spending or duplicate fulfillment. Audience validation for OIDC tokens should always be exact or follow strict prefix rules to avoid substring collisions.
**Prevention:** Always check a persistent store for existing transaction IDs before fulfilling an order. Use strict equality or well-defined prefix checks for security-critical string matching like token audiences.
